# Story 28.1 — Conversation "Voyage" par défaut et messagerie texte

**Titre** : Nouvelle rubrique Chat avec conversation de groupe "Voyage" créée automatiquement, messages texte + emoji horodatés

**Priorité** : P2

---

## Objectif fonctionnel

Donner à la famille un espace de discussion textuelle intégré à l'application, disponible pendant le voyage et après, avec au minimum un groupe par défaut réunissant tout le monde.

## Règles métier exactes

- Une nouvelle rubrique "Chat" apparaît dans la navigation principale (icône dédiée, ex. `MessageCircle` de lucide-react), au même niveau que Guide/Jeu/Résultats.
- À la création de la famille (ou à la première ouverture de la rubrique si la famille existe déjà sans conversation), une conversation de groupe **"Voyage"** est créée automatiquement, contenant tous les profils `proprietaire` et `utilisateur` existants. Elle ne peut pas être supprimée, renommée, ni quittée.
- Tout nouveau profil `utilisateur` créé après coup est ajouté automatiquement à la conversation "Voyage". Les profils `visiteur` n'y sont jamais ajoutés (cf. décision d'accès ci-dessous).
- Un message ne contient que du texte (y compris emoji Unicode via le clavier natif ou un sélecteur d'emoji dans l'app) : **aucune pièce jointe** (image, son, fichier, enregistrement vocal) n'est proposée dans l'interface d'écriture.
- Chaque message affiche l'heure d'envoi (et la date si le message n'est pas du jour), ainsi que le nom de l'auteur dans les conversations à plusieurs (pas nécessaire en 1-to-1). **Exception** : un message envoyé par le profil `proprietaire` affiche toujours l'étiquette **"Organisateur"** à la place de son surnom, dans toutes les conversations où il participe.
- Look and feel façon messagerie mobile (WhatsApp/WeChat) : bulles de message alignées à droite pour les messages de l'utilisateur courant et à gauche pour les autres, couleur de bulle différente par expéditeur ou au moins entre "moi" / "les autres", avatar ou initiale à côté du nom, regroupement visuel des messages consécutifs du même auteur.
- Le rôle `visiteur` n'a pas accès à la rubrique Chat (ni au bouton de nav, ni à un accès direct) : à ajouter dans `access-control.ts` comme les autres sections déjà réservées aux voyageurs (`checklist`, `game`, `results`).

## Modèle de données (proposition)

Suit le pattern déjà en place pour `placeVisitLogs`/`documentPhotos` (chemin dédié hors du snapshot famille principal `families/$familyId`, chargé à la demande, cf. `cloudSyncProvider.ts`) plutôt qu'une intégration au `CloudSyncSnapshot` existant, pour ne pas retélécharger tout l'historique de chat à chaque synchro famille.

```
chatConversations/$familyId/$conversationId
  conversationId: string
  type: "group" | "direct"
  name: string                 // ignoré pour "direct" (nom = l'autre participant)
  isDefaultVoyage: boolean     // true uniquement pour la conversation "Voyage"
  memberProfileIds: Record<string, true>
  createdAt: number
  createdByProfileId: string

chatMessages/$familyId/$conversationId/$messageId
  messageId: string
  conversationId: string
  authorProfileId: string
  authorUid: string
  kind: "text"                 // "poll" en story 28.3
  text: string                 // longueur plafonnée (ex. 2000 caractères)
  createdAt: number
```

Écriture : un profil ne peut écrire un message que dans une conversation dont il est membre (`memberProfileIds`), avec `authorProfileId` = son propre profil et `authorUid` = son `auth.uid` courant (même schéma de vérification par `memberUids` déjà utilisé pour `placeVisitLogs`). Pas d'édition ni de suppression de message dans ce périmètre (voir Hors périmètre).

## Cas limites

- Un profil `utilisateur` est supprimé (story 18.3) : ses messages passés restent visibles avec son surnom figé au moment de l'envoi (même logique que les commentaires de lieux, cf. story 21.2), il est simplement retiré de `memberProfileIds`.
- Le propriétaire quitte son rôle / un nouveau propriétaire est désigné (règle 1 seul propriétaire, cf. BACKLOG-001) : les anciens messages affichés "Organisateur" ne changent pas rétroactivement d'auteur visible ; seul le nouveau propriétaire est étiqueté "Organisateur" pour ses futurs messages.
- Historique long : la liste de messages doit être paginée côté lecture (`limitToLast`, chargement progressif vers le haut), pas de chargement intégral systématique.
- Application rouverte hors ligne : les messages déjà chargés restent visibles (cache local), l'envoi est mis en file et retenté à la reconnexion, cohérent avec le comportement offline déjà en place ailleurs dans l'app.

## Critères d'acceptation testables

1. Un nouveau profil `utilisateur` créé dans une famille existante apparaît automatiquement comme membre de la conversation "Voyage" sans action manuelle.
2. Un profil `visiteur` ne voit pas la rubrique Chat dans sa navigation et un accès direct est refusé avec un message explicite.
3. Un message envoyé par le propriétaire affiche "Organisateur" dans toutes les conversations, jamais son surnom.
4. Un message ne peut contenir qu'une chaîne de texte ; l'interface ne propose aucun bouton d'ajout de photo/son/média dans l'écran de conversation.
5. Chaque message affiche une heure d'envoi correcte, et la date s'affiche si le message date d'un jour différent du jour courant.
6. La conversation "Voyage" ne peut être ni renommée, ni quittée, ni supprimée par aucun profil (y compris le propriétaire).

## Hors périmètre

- Édition ou suppression d'un message déjà envoyé.
- Accusés de lecture individuels ("vu par untel") au niveau du message — seul un compteur de non-lus global est prévu (story 28.4).
- Recherche plein texte dans l'historique des conversations.
- Réactions emoji sur un message (à la différence des réactions déjà existantes sur les défis du jeu, story liée à `CloudChallengeReaction`).

## Priorité

P2

## Validation attendue

Tests unitaires (création automatique de la conversation "Voyage", ajout d'un nouveau profil), tests de règles RTDB (écriture réservée aux membres, `authorUid`/`authorProfileId` cohérents), test d'intégration App (accès refusé visiteur, affichage "Organisateur"), test manuel du rendu visuel (bulles, horodatage) sur mobile.

## Contraintes UX

Ton et densité visuelle cohérents avec le reste de l'app (mobile-first, cartes/bulles arrondies). Le badge "Organisateur" doit être visuellement discret mais clair (ex. petit libellé sous le nom de bulle), sans donner l'impression d'un rôle "administrateur" intrusif.

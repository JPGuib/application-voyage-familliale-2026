# Story 29.1 — Infos du groupe

**Titre** : Un pense-bête/fil d'annonces partagé par le groupe, distinct de l'agenda de visite

**Priorité** : P2

---

## Objectif fonctionnel

Permettre à chacun de partager au groupe des informations pratiques ponctuelles (heure de lever, heure de départ, "ne pas oublier X", "RDV dans 30 minutes"...) sans les mélanger avec l'agenda de visite (programme touristique) ni avec le Chat (conversation, pas fait pour des rappels qui doivent rester visibles plusieurs jours). Backlog d'origine : `docs/Backlog Appli.txt`, item **AGENDA - AG1**.

## Règles métier exactes

- Rubrique dédiée **"Infos du groupe"** (icône `StickyNote`), distincte de l'Agenda de visite et du Chat.
- **Accès** :
  - Propriétaire : accès total, à tout moment (avant et pendant le séjour).
  - Utilisateur (voyageur) : accès en écriture/lecture, **avant ET pendant** le séjour (contrairement au Chat qui n'ouvre qu'au démarrage du voyage) — permet de préparer des annonces à l'avance.
  - Visiteur : **aucun accès**, ni lecture ni écriture (même traitement que le Chat, `isChatEligibleRole`).
- **Un item** = jour du voyage + heure libre optionnelle (texte non structuré, ex. "7h00") + texte + auteur (surnom figé à la création, "Organisateur" pour le propriétaire, cf. `resolveChatAuthorSnapshotLabel` réutilisé du Chat) + épinglé (oui/non) + coche "fait" **individuelle par profil**.
- **Édition/suppression** : l'auteur peut modifier/supprimer son propre item ; le propriétaire peut modifier/supprimer n'importe quel item.
- **Épinglage** : réservé au propriétaire, indépendamment de l'auteur de l'item.
- **Coche "fait"** : chaque profil éligible coche sa propre entrée, indépendamment des autres — ne marque jamais le tableau comme "lu" (indépendant du badge non-lu, voir plus bas).
- **Tri/affichage** : les items épinglés apparaissent toujours en tête (section "Épinglé"), peu importe le jour ; le reste est groupé par jour croissant, puis heure (les items avec heure renseignée avant ceux sans), puis ordre de création.
- **Jours passés** : repliés par défaut (jour strictement avant le jour courant du voyage), révélés via un bouton "Voir les jours précédents" (bascule, état local à l'écran, non persisté). Le jour courant et les jours futurs restent toujours visibles.
- **Badge non-lu** : sur l'icône de navigation, dès qu'un item plus récent que le dernier passage du profil existe — même mécanisme que le Chat (story 28.4), mais sur un tableau unique (pas de dimension "conversation").
- **Suppression** : définitive (pas d'historique conservé).

## Modèle de données

```
groupInfoItems/$familyId/$itemId
  itemId: string
  day: number
  time: string | null           // texte libre, ex. "7h00"
  text: string
  authorProfileId: string
  authorSurnameSnapshot: string // figé à la création
  authorUid: string
  createdAt: number
  pinned: boolean
  doneBy: Record<profileId, true>  // self-write, une clé par profil ayant coché

groupInfoReadState/$familyId/$profileId
  lastReadAt: number
  authorUid: string
```

Stocké hors de `families/$familyId` (même stratégie que le Chat), chargé en continu (pas seulement à la demande) car le badge doit rester à jour même écran fermé. Règles Firebase : auteur/propriétaire pour l'item, propriétaire seul pour `pinned`, self-write strict (vérification d'identité via `profiles/$profileId/memberUids`) pour `doneBy/$profileId` et pour `groupInfoReadState/$profileId` — plus strict que le `chatReadState` existant, qui ne vérifiait que l'appartenance à la famille et pas l'identité exacte.

## Cas limites

- Un item sans heure renseignée (`time: null`) : affiché après ceux qui en ont une, dans le même jour.
- Le propriétaire modifie/supprime un item d'un autre profil : autorisé, sans confirmation supplémentaire dans ce périmètre.
- Un profil non-owner tente d'épingler ou d'éditer l'item d'un autre : bloqué côté UI (bouton absent) et côté règles Firebase.
- Champ `time` optionnel : absent de la liste des champs obligatoires de l'allowlist Firebase, mais validé (longueur, type) si présent.

## Critères d'acceptation testables

1. Un visiteur ne voit pas du tout la rubrique dans le menu.
2. Le propriétaire peut épingler/éditer/supprimer n'importe quel item, y compris ceux des autres.
3. Un utilisateur non-owner ne peut éditer/supprimer que ses propres items.
4. La coche "fait" est strictement individuelle : deux profils cochant le même item ont un état indépendant.
5. Les jours passés sont repliés par défaut ; "Voir les jours précédents" les révèle ; le jour courant et les jours futurs restent toujours visibles.
6. La section "Épinglé" reste visible en tête, peu importe le jour affiché/replié.
7. Le badge de navigation apparaît sur nouvel item non lu et disparaît après ouverture de l'écran.
8. La rubrique est accessible et utilisable avant le début du voyage (contrairement au Chat), sauf pour le visiteur qui n'y a jamais accès.

## Hors périmètre

- Historique d'édition (une modification écrase le texte en place).
- Heure structurée/vrai sélecteur d'heure (texte libre uniquement, pas d'analyse chronologique réelle).
- Notification push hors application (même limite que le badge Chat, story 28.4).

## Contraintes UX

Distinction visuelle claire avec le Chat et l'Agenda de visite (icône `StickyNote` dédiée) ; style visuel de la coche "fait" inspiré du badge "✓ Vu" du Guide du séjour, mais avec une logique inversée (chacun coche pour soi, jamais pour un autre) ; section "Épinglé" mise en avant (bordure verte) au-dessus du fil chronologique.

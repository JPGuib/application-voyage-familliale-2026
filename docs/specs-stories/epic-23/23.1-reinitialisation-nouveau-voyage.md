# Story 23.1 — Réinitialisation "nouveau voyage"

**Titre** : Permettre au propriétaire de réinitialiser la progression du voyage sans perdre les profils

**Priorité** : P3

---

## Objectif fonctionnel

Permettre à la famille de réutiliser l'application pour un futur voyage, en réinitialisant le contenu spécifique au voyage en cours (checklist, historique de jeu, phase, date de départ), sans perdre les profils, rôles et code propriétaire déjà configurés.

## Règles métier exactes

- Action réservée au propriétaire, accessible depuis Paramètres, cohérente avec les autres actions sensibles de l'app (ex. gestion du code propriétaire).
- La réinitialisation efface : la progression checklist de tous les profils, l'historique de jeu (`GameHistoryEntry`) de tous les profils, la phase du voyage (avant/pendant), et la date de début du voyage (`tripStartDate`).
- La réinitialisation conserve : les profils existants (surnoms, rôles owner/user), le code propriétaire et sa phrase de récupération.
- Une confirmation explicite à deux étapes est requise avant réinitialisation (action destructrice et irréversible pour les données du voyage).
- Le contenu du voyage lui-même (destinations, lieux, quiz) reste piloté par le code/contenu de l'app (`content/places.ts`, `docs/jours-destinations.csv`) — cette story ne couvre pas un éditeur de contenu, seulement la remise à zéro de la progression.

## Cas limites

- Réinitialisation demandée alors que des profils sont connectés sur d'autres appareils en simultané → tous les appareils doivent refléter l'état réinitialisé, cohérent avec l'architecture family-wide déjà en place (stories 1.3/1.4/11.3).
- Réinitialisation par erreur → nécessite une confirmation forte (idéalement re-saisie du code propriétaire) avant exécution, pas une simple case à cocher.
- Contenu du prochain voyage différent (nouvelles destinations) → hors périmètre de cette story, nécessiterait une mise à jour du code/contenu de l'app en parallèle (comme cela a été fait pour la Turquie, story 4.2).

## Critères d'acceptation testables

1. Seul le propriétaire voit et peut déclencher l'action de réinitialisation dans Paramètres.
2. Une confirmation forte (au moins deux étapes, incluant idéalement le code propriétaire) est requise avant exécution.
3. Après réinitialisation : checklist à 0 % pour tous les profils, historique de jeu vide, phase revenue à "avant voyage", pour tous les appareils de la famille.
4. Après réinitialisation : les profils, rôles et code propriétaire restent inchangés — aucun profil n'a besoin d'être recréé.

## Hors périmètre

- Édition du contenu du prochain voyage (destinations/lieux/quiz) depuis l'app — reste un travail de contenu/code, comme pour ce voyage.
- Historisation/archivage du voyage précédent avant réinitialisation (export du bilan) — pourrait être une story complémentaire future, non couverte ici.

## Priorité

P3 — pas urgent tant qu'un seul voyage est prévu, mais peu coûteux à spécifier dès maintenant.

## Validation attendue

Tests unitaires (portée exacte des données effacées vs conservées), test d'intégration multi-profils/multi-appareils, test manuel avec confirmation forcée.

## Contraintes UX

Ton rassurant mais clair sur le caractère irréversible ("Cette action effacera la progression de TOUTE la famille pour ce voyage. Les profils resteront."), pas un simple bouton discret dans un sous-menu perdu.

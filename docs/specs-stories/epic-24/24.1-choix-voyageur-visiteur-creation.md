# Story 24.1 — Choix Voyageur/Visiteur à la création de profil

**Titre** : À la création d'un profil (hors premier profil propriétaire), demander si la personne est "Voyageur" ou "Visiteur", et valider le code voyageur si "Voyageur" est choisi

**Priorité** : P2

---

## Objectif fonctionnel

Formalise l'idée notée dans `docs/Backlog Appli.txt` ("Avoir des utilisateurs qui sont des visiteurs avec des droits plus restreints... faut-il créer les utilisateurs famille avant ?"). Réponse apportée par cette story : non, l'ordre de création ne compte pas — c'est la saisie du code voyageur au moment de la création qui distingue un membre de la famille (Voyageur) d'un visiteur externe. Aujourd'hui, tout profil créé après le propriétaire devient automatiquement "utilisateur" (`assignRoleOnProfileCreation`, `owner-policy.ts`), sans distinction entre un membre de la famille qui voyage et une personne extérieure qui souhaite simplement suivre le voyage.

## Règles métier exactes

- Premier profil créé (aucun propriétaire existant) → devient propriétaire, inchangé (stories 1.1/8.1), non concerné par cette question.
- Tout profil créé ensuite doit répondre à "Voyageur ou Visiteur ?" avant de finaliser sa création.
- **Voyageur** → doit saisir le code voyageur configuré par le propriétaire (story 24.2). Code correct → profil créé avec le rôle "utilisateur" (comportement actuel inchangé : checklist, guides, jeu comptabilisé).
- **Visiteur** → aucun code requis, profil créé avec un nouveau rôle "visiteur" (droits définis en story 24.3).
- Code voyageur incorrect → message d'erreur ; la personne peut réessayer ou basculer sur "Visiteur" (pas de blocage total de la création de profil).
- Aucun code voyageur encore configuré par le propriétaire → l'option "Voyageur" affiche un message explicite ("Le propriétaire doit d'abord configurer un code voyageur dans ses paramètres") ; seule l'option "Visiteur" est immédiatement utilisable.

## Cas limites

- Migration des profils "utilisateur" déjà existants avant cette story → restent "utilisateur" (= voyageurs) sans ressaisie de code, aucune régression.
- Propriétaire qui change le code voyageur après coup → n'affecte pas les profils déjà créés, seulement les prochaines créations.
- Tentatives répétées de code voyageur incorrect → pas de verrouillage strict nécessaire (contexte familial), mais un léger anti-brute-force est recommandé, cohérent avec le verrouillage déjà existant sur le code propriétaire (`lockRemainingSec`).

## Critères d'acceptation testables

1. Après le premier profil (propriétaire), toute création de profil demande "Voyageur ou Visiteur ?" avant validation.
2. Choisir "Voyageur" avec le bon code crée un profil de rôle "utilisateur", comme aujourd'hui.
3. Choisir "Voyageur" avec un mauvais code affiche une erreur et ne crée pas le profil ; la personne peut réessayer ou basculer sur "Visiteur".
4. Choisir "Visiteur" crée un profil de rôle "visiteur" sans code requis.
5. Si aucun code voyageur n'est configuré, l'option "Voyageur" indique clairement la marche à suivre plutôt que d'échouer silencieusement.

## Hors périmètre

- Les droits d'accès du rôle "visiteur" une fois créé (story 24.3).
- La configuration du code voyageur par le propriétaire (story 24.2).

## Priorité

P2

## Validation attendue

Tests unitaires (logique de choix de rôle et validation du code), test d'intégration du flow de création complet, test manuel avec code correct/incorrect/absent.

## Contraintes UX

- La question doit être posée simplement (ex. deux gros boutons "Je voyage avec vous" / "Je veux juste suivre le voyage"), sans jargon technique.

## Note technique

`enforceOwnerUniqueness` (`owner-policy.ts`) force aujourd'hui tout profil non-propriétaire au rôle "utilisateur" à chaque chargement (recalcul de l'état partagé). Cette fonction doit être adaptée pour préserver le rôle "visiteur" et ne plus l'écraser, sans quoi tout profil visiteur redeviendrait "utilisateur" au rechargement — point de vigilance à signaler au Dev avant chiffrage.

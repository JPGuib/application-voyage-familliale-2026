# Story 27.4 - Lecture offline cohérente et non-régression sur la visibilité propriétaire

Status: review
Epic: 27 - Offline traveler mode
Story Key: 27-4-lecture-offline-coherente-contenu-visibilite
Date: 2026-08-06
Priority: P1

## Story
As a traveler profile user,
I want the six content screens (Guide de séjour, Documents, Histoire, Géographie-économie, Culture-tradition, Conseils) to behave the same offline as online — including the owner's visibility rules — and to tell me clearly what is and isn't available locally,
so that going into airplane mode never produces a blank screen, a silent gap, or a way to see content the owner has hidden.

## Business Value
- Turns story 27.2's download flow and story 27.3's storage-persistence hardening into a trustworthy *reading* experience offline, not just a working download screen.
- Prevents a visibility regression: without this story, "offline" could accidentally become a loophole to view owner-hidden places/documents if the filtering logic were ever bypassed for cached content.
- Avoids the worst offline failure mode for a family on a trip: a place or document silently missing/broken with no explanation and no way to know if that's expected.

## Acceptance Criteria
1. In airplane mode, after a complete download, the six sections display text, images and audio normally.
2. A non-owner profile sees, offline, neither more nor fewer places/documents than it would see online at the same instant.
3. Direct/restored access offline to a place hidden by the owner is blocked the same way as online (safe redirect, explicit message) — no bypass via absence of network.
4. Partially downloaded content shows an explicit state ("Disponible hors ligne" / "Partiellement disponible hors ligne" / "Nécessite une connexion") rather than a silently missing media.
5. No regression on the existing visibility integration suites (`App.place-visibility.integration.test.tsx`, `App.document-visibility.integration.test.tsx`).
6. Toggling online ↔ offline while a content screen is open causes neither a blank screen nor loss of already-displayed content.

## Scope
### In scope
- A pure, unit-tested helper (`getSectionOfflineAvailability`) deriving the French "disponible hors ligne / partiellement disponible / nécessite une connexion" state for a content section from the existing story 27.2 registry (`sectionProgress`) and the current connectivity state — no new tracking store, no per-resource duplication of that registry's logic.
- A shared `ContentOfflineStatusBadge` UI component, reused by all six content screens (via the two shared renderers `ContentListScreen`/`ContentDetailScreen`, plus `GuideScreen`, `DocumentsScreen`, `TipsScreen` directly).
- Threading the app's existing `isOnline` state as a prop into all six screens and their detail sub-screens (Place, Histoire/Géographie/Culture topic detail), so the badge/guard behavior is available everywhere without introducing a second connectivity hook.
- Verification (via new tests, no code change since the guard is pre-existing and correct) that the place visibility guards (`isPlaceVisibleForRole` filtering in `GuideScreen`/`PlanningScreen`, the `openPlace` guard, and the deep-link/restored-state effect guard) keep working identically regardless of `navigator.onLine`.
- Verification that the audio player (`new Audio(item.audioSrc)` in `ContentDetailScreen`) needs no code change to work from Cache Storage, since the Workbox `CacheFirst` runtime-caching rule for `/images/` and `/audio/` (in `vite.config.ts`) already serves those requests from the same `offline-media-v1` cache that story 27.2 writes to.

### Out of scope
- Any modification of the visibility filtering logic itself (`isPlaceVisibleForRole`, `isDocumentVisibleForRole`, stories 26.2/26.3) — already stable, this story only verifies its offline continuity.
- Per-resource (single photo/single audio file) gap indicators inside a place/topic detail screen — the badge operates at the section level, matching the story's constraint to reuse the story 27.2 registry "sans dupliquer cette logique" rather than build a second, finer-grained tracking mechanism.
- The game, checklist, tutorial, settings (outside this epic's perimeter).
- Deduplicating the pre-existing `isOnline` detection duplicated between `App.tsx` and `MapScreen.tsx`'s local `useIsOnline()` — unrelated to this story's scope and not touched.

## Developer Guardrails

### Technical Requirements
- Reuse `OfflineSectionKey` / `OfflineDownloadRegistry` / `readOfflineDownloadRegistry()` from `src/app/offline-media.ts` (stories 27.2/27.3) as the single source of truth; add only a new pure derivation function there, no second registry.
- No blocking network dependency on the initial render path of any content screen (no `await fetch` on mount) — the badge is computed synchronously from the already-local registry read (`useMemo`, matching the existing `DashboardScreen` pattern at its own offline-summary `useMemo`).
- Default to "nothing to show" (`null` badge) whenever a section has not been downloaded yet **and** the device is online — avoids false alarms; only surfaces a warning ("Nécessite une connexion") when that gap would actually bite, i.e. while offline.
- Do not touch the existing `ContentDetailScreen` audio effect/error-handling — it already surfaces a generic French error message on load failure and must keep working unmodified per the story's own constraint.

### Architecture Notes
- Two shared renderers cover 4 of the 6 sections: `ContentListScreen` (Histoire/Géographie-économie/Culture-tradition lists) and `ContentDetailScreen` (Place/Histoire-topic/Géographie-topic/Culture-topic detail) each gained an `offlineSection: OfflineSectionKey` + `isOnline: boolean` prop, so the badge is wired once per shared component rather than six times.
- `GuideScreen`, `DocumentsScreen`, `TipsScreen` are bespoke (not built on the shared renderers) and each received the `isOnline` prop and their own `ContentOfflineStatusBadge` call directly.
- `App.tsx` renders most screens at **two** call sites (an `if (effectiveScreen === ...)` chain and an equivalent `switch (effectiveScreen)` chain) — both had to receive `isOnline={isOnline}` for every affected screen; missing one of the two sites was the actual bug caught during red-green testing (see Debug Log).
- The offline-availability badge tone/label mapping: registry section `status === "complete"` → "Disponible hors ligne"; `"partial"` → "Partiellement disponible hors ligne" (shown regardless of connectivity, as a standing readiness indicator); `"not-downloaded"` → `null` while online (no false alarm) or "Nécessite une connexion" while offline.
- The place visibility deep-link guard (`App.tsx`, effect reacting to `[screen, selectedPlaceId, profile.role, placeVisibilityMap]`) needed no change: it only reads local React state, never network, so it already fires identically offline — confirmed by a new integration test that flips connectivity and replays a "hidden by owner" snapshot update while the profile is mid-navigation.

### Edge Cases
- Content partially downloaded (e.g. images present, audio missing for a place): the section-level badge reports "Partiellement disponible hors ligne"; the pre-existing per-resource audio error handler still surfaces the specific missing-audio case without needing new code.
- Online → offline while a content screen is open: `isOnline` is a single piece of App-level state (`window` `online`/`offline` listeners, pre-existing); flipping it only re-renders the badge, it does not remount the screen or discard already-loaded media.
- Offline → online after a period offline: the existing cloud-hydration effect refreshes `placeVisibilityMap`/`documentVisibilityMap` from the next snapshot as before; this story adds no new behavior here beyond confirming the guard still reacts correctly.
- Direct/restored access to a hidden place while offline: same guard as online, using whatever `placeVisibilityMap` value is currently in local state (last known good value) — no network contact attempted or required.

# Story 27.5 — Verrouillage des réglages hors-ligne et indication de fraîcheur des données

**Titre** : Désactiver les actions de réglages nécessitant une connexion, et informer l'utilisateur de l'ancienneté des données affichées hors-ligne

**Priorité** : P2

---

## Objectif fonctionnel

Conformément au choix produit (les réglages ne doivent pas pouvoir être modifiés hors-ligne, pour éviter tout risque d'incohérence de synchronisation), désactiver clairement les actions de `SettingsScreen` lorsque l'application est hors-ligne, et informer l'utilisateur que les états sensibles (verrouillage de l'application, visibilité propriétaire) affichés peuvent être ceux d'avant la dernière coupure réseau.

## Règles métier exactes

- Toutes les actions de modification dans `SettingsScreen` (changement de code, verrouillage/déverrouillage, gestion des profils, réinitialisation de score, etc.) sont désactivées (grisées, non cliquables) lorsque `isOnline` est faux, avec un message explicite ("Nécessite une connexion").
- La simple consultation des réglages (lecture seule) reste possible hors-ligne.
- Le reverrouillage de l'application (story 18.1) étant un état cloud partagé family-wide, l'application ne peut pas garantir qu'un appareil hors-ligne reflète l'état de verrouillage le plus récent décidé par le propriétaire : ce point est documenté comme limite acceptée du mode offline, pas comme un bug à corriger dans cette story.
- Un indicateur discret (ex. "Dernière synchronisation : [date/heure]") est affiché lorsque l'application fonctionne hors-ligne, pour que l'utilisateur sache que l'état affiché (visibilité, verrouillage) peut être antérieur à l'instant présent.
- Cette story n'introduit aucune écriture locale en attente pour les réglages : contrairement à la synchronisation cloud du profil/famille (`useCloudSync`), les modifications de réglages restent strictement bloquées hors-ligne plutôt que mises en file d'attente.

## Cas limites

- Passage offline pendant qu'un formulaire de réglages est en cours de saisie : la saisie n'est pas perdue, mais la validation/l'envoi reste bloqué tant que le réseau n'est pas revenu.
- Retour de connexion : les actions de réglages redeviennent disponibles automatiquement, sans nécessiter de rechargement manuel de l'écran.
- Réglages déjà en lecture seule pour un rôle donné (ex. visiteur) : le comportement hors-ligne s'ajoute à la restriction de rôle existante, sans la modifier.

## Critères d'acceptation testables

1. Hors-ligne, toutes les actions de modification des réglages sont visiblement désactivées, avec un message explicite.
2. En ligne, le comportement des réglages est strictement identique à aujourd'hui (aucune régression).
3. Un indicateur de dernière synchronisation est visible en mode hors-ligne.
4. Le retour de connexion réactive les actions de réglages sans action manuelle de l'utilisateur.

## Hors périmètre

- Toute mise en file d'attente locale des modifications de réglages effectuées hors-ligne (délibérément exclu, à la différence de la synchronisation cloud du profil/famille).
- La modification du mécanisme de reverrouillage lui-même (story 18.1), non touché ici.

## Priorité

P2

## Validation attendue

- Tests unitaires : état désactivé/activé des actions de réglages selon `isOnline`.
- Test manuel : bascule online/offline pendant la consultation des réglages.

## Contraintes UX

- Le message de blocage doit être informatif et non alarmiste (cohérent avec le ton familial de l'application), par exemple proche du style déjà utilisé pour `OfflineBanner`.
- L'indicateur de fraîcheur des données doit rester discret, ne pas donner une impression d'erreur alors qu'il s'agit d'un fonctionnement attendu.

# Story 25.4 — Parcours vidéo "On est parti !" après déblocage

**Titre** : Remplacer l'attente pré-départ par un écran central "On est parti !" et imposer une vidéo de lancement une fois l'application débloquée

**Priorité** : P1

---

## Objectif fonctionnel

Créer un parcours de lancement familial autour d'un écran unique centré sur le message **"On est parti !"**. Tant que le voyage n'a pas démarré, les profils non propriétaires restent sur cet écran. Dès que le propriétaire débloque l'application, les profils non propriétaires peuvent lancer une vidéo d'ouverture (`voyage_istanbul.mp4`), puis choisir soit de la revoir, soit d'entrer dans l'application. Le propriétaire, lui, ne doit jamais être forcé à voir cette vidéo.

## Règles métier exactes

- Tant que l'application est bloquée (`phase === "before"`), tous les profils **non propriétaires** voient un écran plein cadre avec un **unique bouton central** de type **"On est parti !"**.
- Si un profil non propriétaire clique sur ce bouton alors que l'application est encore bloquée, aucun lancement vidéo n'a lieu et un message explicite indique que **le voyage n'a pas encore démarré**.
- Dès que le propriétaire débloque l'application, les profils `utilisateur` **et** `visiteur` voient ce même écran central, mais le bouton lance alors la vidéo `voyage_istanbul.mp4`.
- La vidéo source est fournie par la famille sous `/docs/voyage_istanbul.mp4`. Le détail technique de publication web (copie vers `public/`, import Vite, pipeline build) est libre tant que la source éditoriale reste ce fichier.
- Si la vidéo est absente, introuvable ou illisible, l'application doit automatiquement basculer vers un **parcours de secours** composé d'écrans successifs à faire défiler avec un bouton **"Next"** (ou équivalent), conçu pour **simuler la vidéo** sans bloquer le lancement du voyage.
- Ce parcours de secours doit être **créé** dans l'application comme un vrai contenu éditorial de remplacement, avec plusieurs étapes ordonnées, et il remplit exactement le même rôle de sas d'entrée que la vidéo.
- À la fin de la vidéo, deux choix uniquement sont proposés :
  - **Revoir la vidéo**
  - **Entrer dans l'application**
- À la fin du parcours de secours, les mêmes deux choix uniquement sont proposés :
  - **Revoir la séquence**
  - **Entrer dans l'application**
- Choisir **Entrer dans l'application** redirige vers l'écran d'accueil (`dashboard`) avec les droits normaux du profil courant :
  - `utilisateur` -> droits voyageur habituels
  - `visiteur` -> droits visiteur restreints déjà définis par la story 24.3
- Le **propriétaire** ne voit jamais cette vidéo dans son parcours normal :
  - si l'application est verrouillée, il conserve ses accès complets conformément à la story 18.2 ;
  - si l'application est déverrouillée, il arrive directement sur l'application sans étape vidéo obligatoire.
- Une fois qu'un profil non propriétaire a choisi **Entrer dans l'application**, la vidéo n'est plus consultable librement depuis l'application pendant ce cycle de voyage.
- Seul le propriétaire peut relancer la vidéo après coup, depuis son écran Paramètres.
- Si le propriétaire **rebloque** l'application puis la **débloque** à nouveau, le même processus repart à zéro pour tous les profils non propriétaires :
  - écran "On est parti !" pendant le blocage ;
  - vidéo à regarder de nouveau après le prochain déblocage avant d'entrer dans l'application.

## Cas limites

- Un visiteur créé avant le déblocage voit lui aussi l'écran "On est parti !" pendant le blocage, même si la story 24.3 lui donne par ailleurs un accès plus large : cette story introduit une **exception explicite pré-départ** pour préserver l'effet de lancement.
- Un visiteur ou utilisateur qui ferme l'application en cours de vidéo ou en cours de séquence de secours puis revient avant d'avoir choisi **Entrer dans l'application** doit reprendre sur le parcours de lancement du cycle courant, pas arriver directement sur l'accueil.
- Si le propriétaire débloque l'application pendant qu'un autre profil est déjà sur l'écran "On est parti !", ce profil doit pouvoir lancer la vidéo sans rechargement manuel.
- Si le fichier vidéo est absent, introuvable ou illisible, l'application ne doit pas afficher un écran d'erreur bloquant : elle doit basculer directement sur la séquence de secours en écrans successifs.
- La séquence de secours doit rester volontairement simple : un écran à la fois, un contenu lisible, un bouton **Next** pour avancer, et la possibilité finale de **revoir** ou **entrer dans l'application** comme après la vidéo.
- Si le propriétaire rebloque l'application alors qu'un profil non propriétaire a déjà terminé la vidéo et se trouve dans l'application, ce profil est immédiatement renvoyé vers l'écran "On est parti !" cohérent avec le nouvel état verrouillé.
- Si le propriétaire rebloque l'application alors qu'un profil non propriétaire a déjà terminé la vidéo ou la séquence de secours et se trouve dans l'application, ce profil est immédiatement renvoyé vers l'écran "On est parti !" cohérent avec le nouvel état verrouillé.
- La fin de vidéo doit être détectée de façon fiable sur web mobile et desktop ; si l'événement de fin n'est pas reçu, un contrôle explicite de fin/relecture doit rester disponible.
- La séquence de secours doit offrir un état de progression déterministe même sur navigateur lent ou hors-ligne partiel, sans dépendre du chargement média.

## Storyboard détaillé du fallback "Next"

Quand la vidéo n'est pas lisible, la séquence de secours doit reprendre le script narratif ci-dessous, écran par écran.

### Écran 1

- **Titre** : Bienvenue !
- **Texte** : Notre voyage démarre à Istanbul pour découvrir la Turquie.
- **Action** : bouton `Next` pour passer à l'écran 2.

### Écran 2

- **Texte** : Nous traverserons ensuite Ankara, capitale moderne bâtie sur les fondations d'une histoire antique, avant de nous émerveiller devant les paysages presque irréels de la Cappadoce, sculptés par les volcans et le temps.
- **Action** : bouton `Next`.

### Écran 3

- **Texte** : Le voyage nous conduira ensuite vers les terrasses blanches de Pamukkale, les vestiges grandioses d'Éphèse, les rivages de la mer Égée à Izmir, avant de terminer à Bursa, première capitale de l'Empire ottoman nichée au pied de montagnes majestueuses.
- **Action** : bouton `Next`.

### Écran 4

- **Texte** : Au fil des kilomètres, nous traverserons des civilisations, des empires, des traditions vivantes et des paysages parmi les plus spectaculaires du monde. Entre mosquées, palais, cités antiques, vallées extraordinaires et marchés animés, chaque étape nous racontera une nouvelle facette de ce pays unique.
- **Action** : bouton `Next`.

### Écran 5

- **Texte** : Cette application sera votre compagnon de voyage. Vous y trouverez toutes les informations utiles pour le voyage, mais aussi des guides détaillés en audio, des informations sur l'histoire, la géographie, la culture, les traditions, etc. Mais aussi des quiz quotidiens... que le meilleur gagne !
- **Action** : bouton `Next`.

### Écran 6 (final)

- **Texte** : Alors installez-vous confortablement... Le voyage commence maintenant.
- **Ambiance visuelle** : transition de fond du noir vers le bleu et apparition progressive de photos si disponibles.
- **Action finale** : remplacer `Next` par les deux actions de fin de parcours :
  - `Revoir la séquence`
  - `Entrer dans l'application`

### Règles d'implémentation du storyboard

- Le contenu textuel ci-dessus est la référence produit du fallback MVP.
- L'ordre des 6 écrans est fixe.
- Un seul bouton principal de progression est affiché par écran (sauf écran final qui affiche les deux actions de sortie).
- La progression doit être mémorisable localement pendant le cycle en cours pour éviter de renvoyer l'utilisateur au début en cas de refresh accidentel.
- Si une future version de la vidéo est modifiée, ce storyboard pourra être aligné dans une story dédiée.

## Critères d'acceptation testables

1. Tant que l'application est bloquée, un profil `utilisateur` ou `visiteur` ne voit qu'un écran central "On est parti !" avec un bouton unique.
2. Cliquer sur ce bouton pendant le blocage n'ouvre pas la vidéo et affiche un message indiquant que le voyage n'a pas démarré.
3. Dès que le propriétaire débloque l'application, ce même bouton ouvre la vidéo `voyage_istanbul.mp4` pour les profils `utilisateur` et `visiteur`, ou la séquence de secours si la vidéo est indisponible.
4. À la fin de la vidéo ou de la séquence de secours, l'utilisateur n'a que deux choix : revoir le contenu de lancement ou entrer dans l'application.
5. Choisir d'entrer dans l'application redirige un `utilisateur` vers l'accueil standard et un `visiteur` vers le même accueil avec ses restrictions de rôle inchangées.
6. Le propriétaire n'est jamais forcé de voir la vidéo ni bloqué par cet écran pour accéder à l'application.
7. Si la vidéo est absente ou illisible, la séquence de secours en écrans successifs est utilisée automatiquement, sans écran cassé ni contournement du sas d'entrée.
8. Après être entré dans l'application, un profil non propriétaire ne peut plus rouvrir librement la vidéo ni la séquence de secours pendant le même cycle de déblocage.
9. Le propriétaire peut relancer cette vidéo, ou à défaut la séquence de secours, depuis ses Paramètres, même après le lancement du voyage.
10. Après un cycle **reverrouillage -> redéverrouillage**, les profils non propriétaires repassent tous par l'écran "On est parti !" puis par le contenu de lancement avant de réaccéder à l'application.
11. Aucune régression n'est introduite sur les droits existants du propriétaire (story 18.2) ni sur les restrictions visiteur après entrée dans l'application (story 24.3).
12. Le fallback reprend le storyboard de 6 écrans défini dans cette story, avec un bouton `Next` à chaque étape puis un écran final proposant `Revoir la séquence` ou `Entrer dans l'application`.

## Hors périmètre

- Montage, compression ou production créative de la vidéo elle-même.
- Production graphique haut de gamme de la séquence de secours ; un premier niveau simple mais propre suffit.
- Sous-titres multilingues, chapitrage ou analytics de visionnage.
- Bibliothèque de plusieurs vidéos de départ ou choix de vidéo par profil.

## Priorité

P1

## Validation attendue

Tests d'intégration du parcours propriétaire/utilisateur/visiteur, tests de persistance sur rafraîchissement et multi-appareils, test manuel desktop + mobile sur lecture/fin de vidéo, test du fallback séquence "Next", test du cycle reverrouillage -> redéverrouillage.

## Contraintes UX

- L'écran "On est parti !" doit être très simple, centré, émotionnel et sans distractions secondaires.
- Tant que le voyage n'a pas démarré, le message de refus doit rester chaleureux et explicite, pas technique.
- Les actions de fin de vidéo doivent être lisibles immédiatement par des enfants ou des adultes peu à l'aise avec le numérique.
- La séquence de secours doit reprendre le même ton émotionnel que la vidéo, avec des écrans courts et un bouton Next évident.

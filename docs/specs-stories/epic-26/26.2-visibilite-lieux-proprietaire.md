# Story 26.2 — Pilotage propriétaire de la visibilité des lieux (surprise)

**Titre** : Permettre au seul propriétaire de masquer/afficher chaque lieu de visite pour tous les autres profils

**Priorité** : P1

---

## Objectif fonctionnel

Le propriétaire doit pouvoir décider, lieu par lieu, si un contenu est visible par les autres profils (voyageur et visiteur) ou caché (effet surprise). Cette décision est globale au niveau famille et se propage sur tous les appareils/profils connectés.

## Règles métier exactes

- Chaque lieu de `PLACES` possède un état de visibilité piloté par le propriétaire :
  - `visible` : le lieu est consultable par tous les profils autorisés au Guide.
  - `hiddenByOwner` : le lieu est caché pour les profils non propriétaires.
- **Seul le propriétaire** peut modifier cet état.
- Les profils voyageur/visiteur n'ont **aucun droit** de modification sur cette visibilité.
- Le propriétaire continue de voir tous les lieux (y compris ceux cachés) pour pouvoir les gérer.
- Le masquage/affichage se propage à toutes les vues concernées :
  - Guide du séjour (liste des lieux par jour)
  - Détail d'un lieu (accès direct / navigation)
  - Planning complet (aperçus des lieux par jour)
- En cas d'accès direct à un lieu caché (URL interne ou état restauré), un non-propriétaire est redirigé vers un écran sûr avec message explicite (pas d'écran vide).
- La fonctionnalité est persistée dans l'état partagé famille (cloud), pas uniquement en local.
- Cette story ne modifie pas la logique du jeu (quiz, énigmes, score, verrouillage du jour).

## Cas limites

- Tous les lieux d'un jour sont cachés :
  - Guide : afficher un état vide explicite (ex. "Pas de visite visible pour ce jour").
  - Planning : la journée reste visible, mais sans badges de lieux cachés.
- Changement de visibilité pendant qu'un autre profil consulte l'app : mise à jour cohérente au prochain snapshot sans erreur de navigation.
- Lieu multi-jours (champ `jour` tableau) : même état de visibilité appliqué à chaque jour où il apparaît.

## Critères d'acceptation testables

1. Un propriétaire peut basculer la visibilité d'un lieu entre visible et caché.
2. Un voyageur/visiteur ne voit aucun contrôle de visibilité et ne peut pas écrire cet état via le client.
3. Un lieu caché n'apparaît pas dans le Guide ni dans le Planning pour les profils non propriétaires.
4. Un lieu caché reste visible pour le propriétaire, avec indicateur de statut.
5. L'état de visibilité est partagé entre appareils et profils (source cloud), sans divergence locale durable.
6. Un accès direct non propriétaire à un lieu caché est bloqué proprement (message + redirection sûre).
7. Aucune régression sur le jeu : mêmes écrans, mêmes scores, mêmes règles de verrouillage.

## Hors périmètre

- Personnalisation de visibilité par profil individuel (ex. visible pour un voyageur mais pas un autre).
- Règles temporelles automatiques (masquer jusqu'à telle date/heure).
- Changement du contenu éditorial de `PLACES`.

## Priorité

P1

## Validation attendue

- Tests unitaires : helpers de filtrage des lieux selon rôle + état de visibilité.
- Tests d'intégration :
  - propriétaire voit tout et peut basculer,
  - voyageur/visiteur voient la version filtrée,
  - propagation cloud entre deux sessions simulées,
  - redirection sûre si lieu caché ouvert en direct.
- Test de non-régression : parcours Jeu inchangé.

## Contraintes techniques

- Étendre le modèle cloud (`CloudSyncSnapshot`/payload) pour stocker la visibilité des lieux.
- Étendre les règles RTDB pour garantir écriture propriétaire uniquement.
- Réutiliser les patterns de garde d'accès déjà présents (`access-control` et redirections sûres) pour éviter les comportements incohérents.
